BGP Next Hop MTU Attribute

Abstract

This document defines NEXT_HOP_MTU, an optional non-transitive BGP path attribute (type code TBD). It carries the IP MTU a speaker promises is acceptable for an NLRI across one network boundary. The speaker that receives the NLRI across that boundary may attach the attribute from the boundary interface MTU and advertise it on internal and external sessions.¶

1. Introduction

Operators often configure a network boundary to accept IP packets larger than 1500 octets (for example, 9000). Internal hosts and routers can use that size only if they learn it. BGP advertises the NLRI but has no way to carry the boundary IP MTU with the route.¶

NEXT_HOP_MTU is an optional, non-transitive path attribute. The speaker that receives an NLRI across a network boundary may attach a 32-bit IP MTU for that boundary and advertise it with the route. The value is a promise that an IP packet of that size, destined to the NLRI, is acceptable across that boundary. It is not a Path MTU ([RFC8201], [RFC1191], [RFC4821]). BGP-LS can carry per-link MTU in a topology ([RFC9552], [I-D.ietf-idr-bgp-ls-link-mtu]); this attribute attaches the promise to an ordinary unicast NLRI.¶

This document uses the BGP terminology of [RFC4271] and [RFC4760]. IP MTU means the largest IP packet, in octets, that can cross a link in one piece (IP header and payload; link-layer framing excluded). Network boundary means the edge interface across which the route was learned and toward which traffic for the NLRI is forwarded.¶

2. NEXT_HOP_MTU Attribute

NEXT_HOP_MTU is optional and non-transitive. IANA assigns the type code (TBD; Section 7). The attribute applies to every NLRI in the UPDATE that carries it. It is a path attribute, not part of the NLRI encoding ([RFC4271], [RFC4760]).¶

The attribute is defined for IPv4 unicast (AFI 1, SAFI 1) and IPv6 unicast (AFI 2, SAFI 1). A speaker MUST NOT attach it to any other AFI/SAFI.¶

2.1. Encoding

The attribute uses the three-octet header of [RFC4271] followed by a four-octet value. The Extended Length bit is clear.¶

When attaching the attribute, the flags octet MUST be 0x80 (Optional set; Transitive, Partial, Extended Length, and reserved bits clear). The length is 4. Unrecognized optional non-transitive attributes are ignored and not propagated ([RFC4271]).¶

IP MTU is an unsigned 32-bit integer in network byte order: the maximum acceptable IP packet size across the network boundary for the NLRI. For IPv4 NLRI the value MUST be in the range 68 to 65535 inclusive ([RFC791]). For IPv6 NLRI the value MUST be in the range 1280 to 4294967295 inclusive ([RFC8200]); values greater than 65535 are for IPv6 jumbograms ([RFC2675]).¶

3. Procedures

3.1. Network Boundary

The network boundary is the interface on which the receiving speaker forwards toward the BGP next hop when that interface is the edge the route was learned across. For a directly connected external session, that is the session interface. The boundary IP MTU is that interface's IP MTU for the NLRI address family.¶

A speaker MUST NOT replace NEXT_HOP_MTU with the MTU of an internal interface when readvertising a route learned across a different edge. For multi-hop external sessions, the speaker MUST NOT invent a boundary from an unrelated interface. It MAY attach a configured promissory value for that neighbor; the configured value MUST be less than or equal to the IP MTU of the interface that forwards toward the next hop.¶

3.2. Attaching on Receipt

A speaker that receives an NLRI across a network boundary MAY attach NEXT_HOP_MTU when installing and when advertising the route, whether or not the route arrived with the attribute. The attached value is computed as follows:¶

  1. Let L be the boundary IP MTU. If L cannot be determined, or is outside the range in Section 2.1 for the address family, MUST NOT attach the attribute.¶
  2. If the received route has a valid NEXT_HOP_MTU value R and local policy accepts R from that neighbor, the attached value is min(L, R); otherwise it is L.¶
  3. Local policy MAY further reduce the value and MUST NOT increase it. The result MUST remain in range for the address family.¶

All NLRI in one UPDATE that carries NEXT_HOP_MTU MUST share the same value; otherwise they MUST be split across UPDATE messages. Absence of the attribute means no promise.¶

3.3. Advertisement

Implementations MUST allow enabling and disabling attachment and acceptance of received values per neighbor and per AFI/SAFI. Neither is required to be enabled by default.¶

On an internal session, a speaker that does not forward the NLRI across a different boundary SHOULD advertise the attribute unchanged when the next hop is unchanged. A route reflector that does not change the next hop SHOULD forward it unchanged ([RFC4456]). The border speaker that attached the value in Section 3.2 SHOULD include that value toward internal peers, including when it sets next hop to self.¶

On an external session, the attached value MUST be the promise for traffic that crosses the boundary with that peer. If the route already has a valid NEXT_HOP_MTU and the speaker knows the facing interface IP MTU, the attached value MUST be the minimum of the two (then reduced by local policy if applicable). A speaker MUST NOT copy a promise for one boundary onto a different boundary without that minimum. If the value cannot be determined, omit the attribute.¶

An originating speaker MAY attach NEXT_HOP_MTU using the IP MTU of the boundary it advertises across, subject to Section 2.1. The receiving speaker may still attach from its own side whether or not the originator sent the attribute.¶

3.4. Use of the Value

Attaching NEXT_HOP_MTU promises that an IP packet destined to a covered NLRI, of size less than or equal to the value, is acceptable across the identified boundary (the interface permits it and the speaker will forward it). Applications MAY use the value when sending toward the NLRI across that boundary. Path MTU Discovery remains required for the minimum MTU of a full path.¶

A speaker MAY program the value as a per-destination forwarding MTU only when every forwarding path for the NLRI carries a valid NEXT_HOP_MTU; the programmed value MUST be the minimum of those path values. Otherwise it MUST NOT program a promissory MTU for the destination.¶

When aggregating, a speaker MAY attach NEXT_HOP_MTU only if every included component has a valid value; the aggregate value MUST be the minimum of the component values. Otherwise omit the attribute from the aggregate.¶

When the boundary IP MTU changes, the speaker that attached NEXT_HOP_MTU from that boundary MUST advertise a replacement route for each affected NLRI with the new value (or omit the attribute if it no longer makes a promise).¶

4. Example

In Figure 2, Router A in AS 65000 advertises 2001:db8::/48 to Router B in AS 65001. The boundary permits an IP payload of 9000 octets. Router B adds NEXT_HOP_MTU with value 9000 (0x00002328) and advertises it to Router C over iBGP. The same receive-and-attach procedure applies in the reverse direction.¶

The boundary addresses (2001:db8:1::1 and 2001:db8:1::2) are outside the advertised prefix. If Router B sets next hop to self toward Router C, NEXT_HOP_MTU remains 9000 because traffic still crosses the same boundary.¶

5. Error Handling

Malformed NEXT_HOP_MTU attributes use attribute discard ([RFC7606]): discard the attribute, process the UPDATE as if it were absent, and MUST NOT session-reset or treat the NLRI as withdrawn. Discard when any of the following holds: the attribute appears more than once; the length is not 4; flags are not exactly 0x80; the value is 0; IPv4 NLRI with value outside 68..65535; IPv6 NLRI with value less than 1280; or AFI/SAFI other than IPv4/IPv6 unicast.¶

6. Operational Considerations

Enable attachment toward the neighbors that should receive the promise, with the boundary interface MTU configured accordingly. If a received value is accepted, the propagated value is min(local boundary MTU, received value). Path MTU Discovery and TCP MSS clamping still apply beyond that boundary.¶

8. Security Considerations

An overstated value can cause packet loss; an understated value reduces efficiency. Deriving the attached value from the local interface MTU limits overstatement by a peer. Accepting a received value can only reduce the attached value (via the minimum) but can propagate an understated promise; operators SHOULD accept received values from external peers only when those peers are trusted. Advertising the attribute reveals a boundary MTU; attachment can be disabled per neighbor if that is sensitive.¶

This document adds no session authentication; see [RFC7454]. Malformed attributes are discarded without resetting the session or withdrawing NLRI (Section 5).¶
